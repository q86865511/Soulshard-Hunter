## 三、獨立驗證揪出、並已修掉的兩個真缺陷

批次 C 只驗不改，發現我在 R28 判定「通過」的 ART-09 有實質漏洞：

1. **beam 所有權在紅綠色盲下失效**：boss `#ff5a3c` 與 event `#ffc23c` 在 protan/deutan 下**色相差 0.1°**，只剩線寬差；箭頭階梯被反鋸齒抹平（event 與 player 同為 8px）。我當初的三色覺驗收只測「光束對背景」，沒測「三族彼此可分」。
   → 批次 D 加**形狀通道**：boss 週期橫檔、event 25% 斷線＋空心箭頭、player 細直＋小箭鏃；achromat 遮罩（顏色不參與）下三族兩兩可分。`bm` 快照通道零變更。
2. **亮/冷生態玩家幾乎不可見**：desert 玩家標識對背景 WCAG **1.06**。根因量測顯示——改前**全場景「被標識畫暗的像素 = 0」**，標識只有加亮單一方向，遇到亮/冷地板必然失效。
   → 加暗通道（環的近黑描邊、beacon 真外框）＋形狀 tick；desert 暗筆畫 0→527px、p90 對比 4.33。beacon 由 N=4 懸崖改 N_SOFT=2 淡入，「密集但未被包圍」空窗的競爭視窗 −23~26%。

**架構師裁決**：接受批次 D 對「desert ≥3:1」判準的重新定義——量「標識筆畫對其實際背景」而非「48×48 patch 平均」。後者要達標必須用近乎不透明的暗塊蓋住玩家周圍，違背判準本意（讓玩家找到自己）。

## 四、DPI 一致性（批次 E——使用者裁決「依建議執行」後完成）

上一版此節為「上報待裁決」的三項，使用者授權後已於批次 E 修畢（全部單點修在 `renderer.js`，
呼叫端零改動；`docs/reviews/art-r29/e-after/E_DPI_REPORT.md`）：

1. **`camera.zoom` 公平性**：zoom 檔位改由 CSS 像素決定再乘 dpr。58 視窗 × 5 DPR 掃描，
   可視世界偏離 dpr1 基準的組合 **182/232 → 1/232**（僅存 1 組 0.03% 的既有 floor 誤差）；
   dpr=1 下兩函式 58/58 逐值相同（no-op 證明）、title 全畫面 SHA 相同。
   取捨（已落檔）：Windows 125%/150% 的非整數 dpr 會有 nearest-neighbor 像素寬度不均——
   此前這些使用者拿到的是不公平的更大視野，公平優先。
2. **`uiScale()` 實體字級**：2.6 上限改在 CSS 空間套。1080p DPR2 的 FONT_BODY 16.90 → 20.65
   CSS px（81.8% → **100.0%**）。
3. **`lw:1` 半亮線**：`uiRect` 對奇數線寬做 0.5 半像素對齊，峰值亮度 **0.489 → 0.912**、
   著色 2 → 1 裝置 px；102 個呼叫端零改動、面板無新縫隙。
