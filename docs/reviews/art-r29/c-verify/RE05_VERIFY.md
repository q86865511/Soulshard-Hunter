## 1. 高 DPI（deviceScaleFactor 2）

擷取矩陣：`{1280×720, 1920×1080} × {dpr1, dpr2} × {title, hub sortie, hub personal,
in-run HUD, 密集戰鬥}` 共 20 張，落 `c-verify/dpr/`；DPR1／DPR2 並排對照
（DPR2 以 LANCZOS 縮回 CSS 尺寸，才是同一物理大小的比較）落 `c-verify/dpr/pairs/`。
密集戰鬥畫面：66 隻敵人（spawn telegraph 已跑完、已朝玩家收攏）＋ 3 條三族 beam。

### 1.1 引擎在 DPR2 下的實測參數（`dpr-metrics.json`）

| 視窗 | dpr | backing store | `camera.zoom` | `uiScale()` | 視野寬(world px) | FONT_BODY 物理字級(CSS px) |
|---|---|---|---|---|---|---|
| 1280×720 | 1 | 1280×720 | 3 | 1.059 | 426.7 | 13.8 |
| 1280×720 | 2 | 2560×1440 | 5 | 2.118 | 512.0 | 13.8 |
| 1920×1080 | 1 | 1920×1080 | 4 | 1.588 | 480.0 | 20.6 |
| 1920×1080 | 2 | 3840×2160 | 6 | 2.600 | 640.0 | 16.9 |

`uiScale()` 在 1280 剛好等於 2.0 倍（1.059→2.118）；在 1920 被 `Math.min(2.6, …)` 夾住
（理想 3.176，實得 2.600）。這條夾限是 1-d 的成因。

### 1.2 imageSmoothingEnabled 與肖像污染（1-a：通過）

- 20 次擷取每次 render 完讀 `ctxRaw().imageSmoothingEnabled` → **全部 false**，
  含 `hub sortie`（該面板會 blit 128×128 肖像 PNG）。
- 更嚴格的污染測試（`_wf_c1_uiprobe.mjs`）：先完整 render 一次 sortie（等 1.8 s 讓 lazy
  portrait fetch 完成後再 render 一次，確保肖像真的畫過），**緊接著用裸 `ctx.drawImage()`**
  （不自己設 smoothing，完全繼承全域狀態）把 `char_hunter` 以整數 6× 貼上，逐格檢查
  6×6 區塊是否嚴格同色 → 四種 viewport/dpr 組合皆 **impure 0 / 288 blocks**。
- 原始碼佐證：全 repo 只有 `src/game/ui/portraits.js:68` 一處開 smoothing，且夾在
  `save()/restore()` 之間、畫完立刻設回 false。
- **目視**：sortie 卡片上的肖像是平滑畫風（毛髮、披風連續漸層），同一張卡上的金幣圖示與
  角色 sprite 邊緣仍是硬邊方塊——兩者在同一畫面同時成立，例外沒有外溢。

### 1.3 半像素模糊（1-b：通過）

Hub 圖示實際是以**非整數**倍率畫的（`2*S`、`2.2*S`、`26*S/w`；見 `scenes/hub/render.js:123,202,230`、
`panels.js:222,232`），所以只測整數倍率不算數。`_wf_c1_frac.mjs` 用真實倍率、目的座標
故意設成小數（40.37, 40.61），統計「目的地出現、但來源調色盤沒有的顏色」（＝插值混色）：

| sprite | 倍率 dpr1 / dpr2 | 取樣像素 dpr1 / dpr2 | 外來色 dpr1 | 外來色 dpr2 |
|---|---|---|---|---|
| char_hunter 16×18 | 2.118 / 4.235 | 830 / 3477 | 0 (0%) | 0 (0%) |
| char_hunter | 2.329 / 4.659 | 1006 / 4200 | 0 | 0 |
| char_hunter | 1.721 / 3.441 | 525 / 2260 | 0 | 0 |
| weapon_w_soulbolt | 三種倍率 | 576–4625 | 0 | 0 |
| coin | 三種倍率 | 228–2897 | 0 | 0 |

**零外來色** ⇒ 沒有任何插值發生，DPR2 沒有半像素模糊。
（非整數倍率造成的是「有些來源像素放大成 4 格、有些 5 格」的粗細不均，不是模糊；
且 DPR2 倍率較大，相對不均反而從 1/2.12≈47% 降到 1/4.24≈24%。）

### 1.4 UI 文字（1-c 通過 / 1-d 未通過）

用真正的 `uiText()` 畫 `Hnl 魂晶 0123`，量 ink bounding box 與「中間調像素占比」

| 1280×720 | 1 | 11.1 | 13.8 | 16.9 | 0.419 / 0.374 / 0.468 |

| 1920×1080 | 2 | **13.7** | **16.9** | **20.8** | 0.322 / 0.293 / 0.238 |

- 1280×720：DPR2 物理字級與 DPR1 完全一致（cap height 差 ≤0.5 CSS px），AA 占比全面下降

- 1920×1080：DPR2 物理字級只有 DPR1 的 **81.9%**（線性；面積 67%），因 `uiScale()` 上限 2.6。

### 1.6 附帶發現：DPR 會改變視野與 sprite 物理大小（1-g）

`renderer.js:34` 的 `Math.round(Math.min(W/430, H/280))` 吃的是 **device** 尺寸，
所以 DPR2 把 zoom 從 3→5（1280）、4→6（1920，且撞到上限 6）：

| 視窗 | 視野(world px) dpr1 → dpr2 | 可視面積 | sprite 物理大小 |
|---|---|---|---|
| 1280×720 | 426.7×240 → 512×288 | **+44%** | −16.7% |
| 1920×1080 | 480×270 → 640×360 | **+78%** | −25.0% |

**目視**（`pairs/pair-run_combat-1280x720.png`）：右半（DPR2）同一批 66 隻敵人明顯畫得比較小、
周圍多露出一圈地圖。這已超出美術範圍——它是**玩法差異**（HiDPI 使用者對逼近的敵人有更多
預警時間），而排行榜是共用的。列此供架構師裁決，我不建議在美術輪動它。

## 2. 「一秒定位」的可量化替代

### 2.0 先講清楚：真人測試沒有做（未能驗證）

複審 RE-05 要求「5 位未看說明的真人測試者、10 秒錄影定位題、答對率 ≥90%」。
**本環境沒有真人受試者也沒有錄影管道，這一項我沒有做，也不用任何方式代稱做過。**
以下是我改用的客觀替代量測；它量的是「畫面上玩家標識相對周圍有多突出」，
**不能**推論反應時間，也**不能**取代真人的答對率。

替代設計三原則：
1. 玩家座標由引擎 `worldToScreen()` 直接給出，不靠影像辨識猜位置 → 量測沒有主觀成分。
2. 一律附對照組：同一格世界，把玩家識別美術在 **runtime** 關掉再 render 一次
   （改 `BALANCE.SCENE_FX` 的 alpha，不動任何檔案），差值即這批美術的貢獻。
3. 用「全畫面滑窗排名」而非只看局部對比——回答「畫面上還有多少地方跟玩家一樣亮／一樣冷」。

### 2.1 玩家定位：10 生態 × 70 敵（2-a：通過，有兩個弱生態）

每生態一格 70 隻敵人、spawn telegraph 已結束、敵群已收攏到玩家身上
（`nearWithinSurroundR` 9–11 隻 ⇒ 10/10 都觸發 surrounded beacon）。
量測：以玩家螢幕座標為心的 48×48 patch vs 周圍 160×160 環帶；滑窗排名以 48×48、stride 8
掃過 play area（扣掉 HUD 邊界），每格 **5304 個視窗**。冷色通道＝B−R（識別色 `#cfeaff` 的方向）。

本項做了**兩輪**：第一輪擷取於 `ee78a13`（批次 A1+B），第二輪重跑於 `bf585cc`

**重複性說明（重要，不要單挑一格數字用）**：兩輪的 *平均值與排序結論* 完全一致，
但**個別生態的 Weber L / 亮度百分位在兩輪間會大幅擺動**（例：cavern 0.275↔0.755、
verdant 0.711↔0.198）——因為那取決於「這一格剛好有哪幾隻敵人壓在玩家旁邊」，
不是生態的固有性質。**穩定的是冷色百分位**（crypt 以外每一格兩輪差 ≤10 個百分點：
frost 24.5/24.6、inferno 95.0/95.6、desert 98.8/98.7、celestial 18.4/18.5），
因為它由該生態的地板色相決定。因此下面的結論只引用**兩輪都成立**的部分。

「同時勝出視窗」＝畫面上同時比玩家**更亮且更冷**的 48×48 視窗數（5304 中），
也就是真正會被誤認的競爭者數量。

判讀：
- **美術有效（兩輪都成立）**：關掉識別美術後競爭者數 59.9 → 139.6（+133%；第一輪
  57.1 → 128.7，+125%），亮度百分位 94.1→88.3、冷色百分位 62.6→48.1。
  20/20 格（10 生態 × 2 輪）全部朝同方向改善，沒有例外。
- **beacon 是主力（兩輪都成立）**：只關 beacon（保留地面光池＋頂環）競爭者已回到 124.0
  （第一輪 116.2），即「密集但未被包圍」時識別強度只比全關（139.6 / 128.7）好約 11%。
- **兩個弱生態**：
  - **desert**：亮度通道幾乎失效（兩輪 Weber 0.074 / 0.025、WCAG **1.06 / 1.02**、
    亮度百分位 72.5% / 60.3% ⇒ 有 1459–2105 個視窗比玩家更亮，十個生態墊底）。
    只靠冷色通道（98.7% / 98.8%，兩輪都是全場最高）撐住 ⇒
    **色覺障礙或灰階／低彩度顯示下，流沙荒漠幾乎無法用標識找到玩家。**
  - **celestial**：冷色通道失效（兩輪 18.5% / 18.4% ⇒ 約 4300 個視窗比玩家更冷，
    因為雲海地板本身就是亮冷藍），競爭者數 243 / 279，是第二名（65 / 62）的約 4 倍，
    亮度百分位 89.3% / 88.8% 也是倒數第二。**天界雲海是兩輪一致的最弱生態。**
  - frost（24.6/24.5）與 abyss（30.6/20.4）的冷色通道同樣弱，但亮度通道 ≥95 百分位補上。
  - 沒有任何生態的兩個通道同時失效。

**目視**（`locate/zoom-locate-onoff-6x.png`，6× 放大、洋紅十字標出真實玩家座標）：
- ON：畫面中央有一圈清楚的淡冷白橢圓（頂層細環）＋一片冷藍地面光池，中央還有被 beacon

  是那圈環和剪影。定位完全依賴這兩個標識，而 beacon 只在「≥4 隻敵人在 14 world px 內」才亮。

### 2.2 三族 beam 所有權（2-b 通過 / 2-c 未通過 / 2-d 部分未通過）

同一格畫面放三條幾何完全相同的水平 beam（boss `#ff5a3c` / event `#ffc23c` / player `#9adcff`），
乾淨背景與 66 敵密集背景各一組，DPR1／DPR2 各一組。

**線寬階梯（2-b：通過）**——見 §1.5：可見寬度 8 / 6 / 4 device px，比例 2.0 : 1.5 : 1.0，
且不隨背景改變（乾淨與密集兩組量到同一組數字）。DPR2 下比例仍成立，只是絕對物理寬度減半。

**箭頭尺寸（2-c：未通過）**——白色實心箭頭實測高度：

| 族 | 規格 aw / ah | 實測白色填充高(device px) dpr1 / dpr2 |
|---|---|---|
| boss | 6.0 / 10.0 | 10 / 10 |
| event | 5.2 / 8.5 | **8 / 8** |
| player | 4.5 / 7.0 | **8 / 8** |

event 與 player 的箭頭在像素上**同高**（8 px），boss 只多 2 px。規格上的 8.5 vs 7.0 差距
經過描邊與整數化後被吃掉 ⇒ 箭頭不構成可用的所有權階梯。

**色相距離與三色覺模擬（2-d：部分未通過）**

以標稱色計（CIELAB ΔE76 / 色相角差）：

| 模擬 | boss↔event | boss↔player | event↔player |
|---|---|---|---|
| 正常 | ΔE 59.2 / 42.5° | 106.9 / 156.8° | 97.4 / 160.7° |
| protanopia 紅色盲 | 44.8 / **0.7°** | 68.3 / 177.7° | 94.8 / 177.0° |
| deuteranopia 綠色盲 | **23.7 / 0.1°** | 83.3 / 176.0° | 96.4 / 175.9° |
| tritanopia 藍黃色盲 | 56.3 / 6.8° | 120.4 / 176.4° | 66.0 / 169.7° |

以**實際畫出來的肩部像素**計（更嚴格，白芯已洗掉部分彩度；密集背景那組）：

| 模擬 | boss↔event | boss↔player | event↔player |
|---|---|---|---|
| 正常 | ΔE 40.0 | 42.2 | 44.5 |
| protanopia | **28.5** | 28.8 | 45.4 |
| deuteranopia | **18.3** | 33.0 | 44.6 |
| tritanopia | 33.0 | 52.9 | **21.3** |

**目視**（`beams/compare-beams-cvd.png`：正常／灰階／protan／deutan／tritan 五組）：
- protanopia 與 deuteranopia：boss 與 event **兩條都變成同一種黃色**，用顏色完全分不開；
  只有 player 那條仍是明顯冷白藍，可以分開。
- tritanopia：boss 變桃紅、event 變粉白，兩者仍能分；反倒 event↔player 靠近（ΔE 21.3）。
- 灰階（完全無色）：三條都變成同一條白灰虛線，**唯一線索只剩線寬**。

結論：
- **boss ↔ player**：顏色（所有模擬 ΔE ≥ 28.8）與線寬（8 vs 4 device px，2.0×）雙重成立 → 可分辨。
- **boss ↔ event**：紅綠色盲下顏色線索歸零（deutan ΔE 18.3、色相差 0.1°），剩下唯一線索是
  **8 vs 6 device px（差 33%）**，箭頭又是 10 vs 8 px。兩條線不同時出現在畫面上時，
  我不認為 33% 的線寬差可被可靠判讀。**RE-05 的「三類 beam 所有權答對率 ≥90%」在紅綠色盲
  情境下，依本量測無法成立**（DPR2 更糟：物理寬度變成 4 vs 3 CSS px）。

### 2.3 哪些情境辨識最弱（誠實結論）

依實測，由弱到次弱：

1. **天界雲海（celestial）＋70 敵**：冷色通道歸零（18.4 百分位、279 個競爭視窗），
   靠亮度 88.8 百分位勉強撐住——十個生態最弱。
2. **流沙荒漠（desert）＋70 敵，且玩家色覺障礙或用低彩度／灰階顯示**：亮度通道歸零
   （WCAG 1.02、60.3 百分位），色相是唯一線索，一旦色相不可用即失效。
3. **密集但「未被包圍」（<4 隻在 14 world px 內）**：beacon 不亮，競爭者數平均 116.2，
   只比完全沒有識別美術（128.7）好 10%。這是結構性缺口——最需要找到玩家的
   「快被淹沒但還沒被包住」那幾秒，正好是保護最弱的時候。
4. **紅綠色盲玩家分辨 boss telegraph 與 event telegraph**：見 §2.2。
5. **1920×1080 HiDPI（DPR2）**：UI 物理字級 81.9%、beam 物理寬度 50%、玩家頂環 1 CSS px
   ——三個弱化疊在同一種使用者身上。

## 4. 方法限制（不要過度解讀本報告）

1. **沒有真人受試者**。全部是像素量測，量的是「突出程度」而不是「找到所需時間」。
   RE-05 的 1 秒／≥90% 驗收條件**沒有被驗證**，只有被替代指標間接支持或反駁。
2. CVD 模擬用 Machado 等人的 severity 1.0 線性矩陣，是近似；真實色覺障礙者的表現可能更好或更差。
3. 密集畫面是人工 spawn 68 隻（收攏後 70）並 pump 110 幀而成，敵種是輪流取樣而非該生態的
   權重池 ⇒ 是**跨生態可比、但不完全等於實戰**的壓力測試。
4. 對照圖的 DPR2 側是 LANCZOS 縮回 CSS 尺寸，會多一層重採樣糊化，真實 HiDPI 螢幕不會有。
   判讀請以「元素的物理尺寸比例」為準，不要以糊化程度為準。
5. 動畫／10 秒錄影定位題（RE-05 提到的動態部分）未做——本工具鏈只能出靜態幀。
6. 本批證據約 53 MB（30 張 4K/2K 原始擷取為大宗，已做無損 PNG 最佳化，99.6→57.7 MB）。
   若不希望全部進版控，可只保留各 `*.json` 與 `compare-*` / `zoom-*` / `sheet-*` / `pair-*`
   派生圖，原始擷取可由腳本重跑重現（世界狀態有固定 seed）。
